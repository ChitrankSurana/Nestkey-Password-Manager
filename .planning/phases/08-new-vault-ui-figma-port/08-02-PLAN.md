<objective>
Give the user the control that selects which frontend the app opens, on both the desktop
app and the localhost web portal.

Purpose: plan 08-01 made the window obey `config.ui_variant`, but the only way to change
that value is to hand-edit a JSON file. This plan completes the setter trail — core → Tauri
command → web route → `api.ts` → Settings UI — so the toggle is a real, discoverable
product feature with the restart semantics D-07 specifies.

Output: the `update_ui_variant` command on both binaries, the `updateUiVariant` API wrapper,
and a new "Interface" section in Settings carrying a select control and a persistent banner.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `/api/update_ui_variant` | An authenticated same-origin HTTP POST from the localhost portal now writes a preference that decides which frontend asset the desktop binary will load at its next launch. |
| Webview → `update_ui_variant` IPC command | The desktop frontend can write the same preference. |
| Settings form value → persisted config | A `<select>` value crosses from untrusted DOM state into a file the Rust boot path reads. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-05 | Tampering | `update_ui_variant` on both the IPC and HTTP paths | high | mitigate | Validation lives once, in `do_update_ui_variant`, which checks the value against `VALID_UI_VARIANTS` before any write. Both transports are pass-throughs, so neither can skip it. The `<select>` is not the control — a crafted IPC call or POST body hits the same allowlist. Covered by the core setter's persist-and-reject test from plan 08-01. |
| T-08-06 | Spoofing | `/api/update_ui_variant` route registration | high | mitigate | The route is registered in the same router chain as its siblings, so it inherits the existing `Extension<Arc<UserSession>>` session requirement and the `X-PWMGR-CSRF` header check. Registering it outside that chain would expose an unauthenticated config write; the acceptance criterion requires it to sit adjacent to `/api/update_mobile_nav_style`. |
| T-08-07 | Elevation of Privilege | Read-only viewer binary | medium | mitigate | The viewer is deliberately excluded (D-06). It lacks `verify_master_password`, so a new UI running there would render reprompt-gated secrets with no way to re-authenticate. Enforced by leaving that crate out of the plan's `files_modified` and by the acceptance criterion that no file under it is modified. |
| T-08-08 | Information Disclosure | Interface banner copy | low | accept | The banner names only the interface label and a local path. It carries no vault data, no username, and no filesystem path outside the app's own routes. |
| T-08-SC | Tampering | npm / cargo package installs | low | accept | This plan installs no new packages in either ecosystem. No package-legitimacy checkpoint is required because there is no install task to gate. |
</threat_model>
