Frontend half of G-08-2, consuming the config plumbing landed by plan 08-11. Today
`SecretField.requestAction` has a bare two-way branch: prompt when the credential's own reprompt
flag is set, otherwise reveal immediately. That branch is correct and stays as the Per-credential
mode. This plan adds the Global mode the UAT's locked decision describes — every credential
prompts, and one correct entry opens a shared grace window — plus the Settings controls to choose
between them.

Purpose: give the user a vault-wide reprompt gate without changing the default for any existing
install.

the `SecretField` rewire, and two Settings controls that take effect immediately.

    `src/lib/repromptPolicy.ts` exports
    `repromptRequired(policy: RepromptPolicy, perCredentialFlag: boolean, lastSuccessAt: number | null, now: number): boolean`.
    `now` and `lastSuccessAt` are epoch milliseconds passed in, never read from the clock inside —
    that is what makes the window logic testable with no fake timers.

    `src/lib/repromptPolicy.test.ts` covers the full truth table:
    - perCredential + flag false -> false (reveal immediately)
    - perCredential + flag true -> true
    - perCredential + flag true + a `lastSuccessAt` one millisecond ago -> still true. The grace
      window must NOT apply in Per-credential mode; the UAT states flagged credentials ask every
      single time. This case is the one a naive implementation gets wrong.
    - global + `lastSuccessAt` null + flag false -> true
    - global + `lastSuccessAt` null + flag true -> true
    - global + `now - lastSuccessAt` strictly inside the window (e.g. 10s elapsed, 30s window) -> false, for
      flag false AND flag true
    - global + elapsed exactly equal to the window -> true (the boundary expires; do not leave it
      ambiguous)
    - global + elapsed beyond the window -> true
    - global + a `lastSuccessAt` in the future (clock moved backwards) -> false is acceptable only if
      deliberate; assert the chosen behavior explicitly rather than leaving it undefined, and prefer
      treating a negative elapsed time as "window open" since it cannot be attacker-induced in a
      local-only single-user app.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user -> reauth modal | the master password is re-entered here while the vault is already unlocked |
| grace window state -> every mounted SecretField | one credential's successful verification relaxes the gate for all of them |
| lock event -> grace state | the window must not survive a lock |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-12-01 | Elevation of Privilege | grace window in `src/lib/reprompt.ts` | medium | mitigate | An open window relaxes the gate for every credential, so it must be bounded and must die with the session. Mitigated by an allowlisted maximum of 300s (enforced in Rust by plan 08-11, so a hand-edited config cannot exceed it), `clearRepromptGrace()` on the `vault-locked` event in both app shells, and in-memory-only state that a reload resets. Tested by the exact-boundary expiry row in Task 1 and gated by greps in Task 2. |
| T-08-12-02 | Spoofing | `markRepromptSuccess` placement in `confirmReauth` | high | mitigate | Opening the window on a failed or errored verification would let a wrong password unlock every secret for 30s. Task 2 places the call after the `ok === true` check and after the existing early return for a wrong password, inside the success path only. |
| T-08-12-03 | Tampering | `isRepromptRequired` default before config loads | low | accept | Until `ensureRepromptConfig()` resolves, the policy is the Per-credential default, so a Global-mode user could in principle reveal one non-flagged secret in that window. Accepted deliberately: `SecretField` triggers the load on mount and the vault view mounts long after the shell's own config read; the alternative (prompt for everything until loaded) would regress Per-credential users, who are the default and the majority. The gate protects an already-unlocked vault whose secrets are already in the DOM, so this is a convenience control, not a boundary. |
| T-08-12-04 | Information Disclosure | `src/lib/reprompt.ts` module state | low | mitigate | The store holds only a policy enum, an integer, and a timestamp — never the master password, never a secret. `confirmReauth`'s existing `setPassword("")` on success stays untouched. |
| T-08-12-05 | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — no package is installed. Every construct used already exists in the codebase. No package-legitimacy checkpoint required. |
</threat_model>
