<objective>
Backend half of G-08-2. The UAT established that the reported symptom was not a bug — the tested
credential simply had its per-credential reprompt flag off, and the existing gate behaved
correctly. The locked decision from that session is to add a new Settings-level choice instead of
changing per-credential defaults:

- **Per-credential** (default, today's behavior): only credentials with "Require reprompt" on ask
  for the master password, and they ask every single time.
- **Global**: every credential's reveal/copy requires the master password, and a correct entry
  opens a grace window (default 30s, configurable) during which further reveals/copies for ANY
  credential do not re-prompt.

No scaffolding for this exists anywhere in the repo. This plan lands the persisted config, the
DTO, the validated setters, both transports, and the frontend API wrapper. Plan 08-12 consumes
them in `SecretField` and Settings.

Purpose: keep the storage/validation/transport work in one reviewable unit and out of the same
context as the UI gate logic.

Output: `repromptMode` and `repromptGraceSeconds` fully wired from `config.json` to `src/lib/api.ts`,
with the default reproducing today's behavior exactly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `~/.pwmgr/config.json` -> `Config::load` | a file the user (or any local process) can hand-edit becomes in-process policy |
| browser -> `/api/update_reprompt_*` | an untrusted client can request a weaker reprompt policy |
| frontend -> Tauri IPC setters | same request, over the desktop transport |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-11-01 | Tampering | `Config::load` snapping in `core/src/config.rs` | medium | mitigate | A hand-edited or corrupted `config.json` could set a nonsense mode or an enormous grace window, effectively disabling the reprompt gate. Task 1 snaps any out-of-allowlist value for either field back to its default on load, and the grace window is an allowlisted enum rather than a free integer so no arbitrarily long window is representable. Two `Config::load` tests gate this. |
| T-08-11-02 | Elevation of Privilege | `/api/update_reprompt_mode` | medium | mitigate | A web request could weaken the gate to `perCredential`. Both handlers keep the `Extension<Arc<UserSession>>` extractor every sibling uses, so an unauthenticated caller cannot reach them, and the validated setters accept only allowlisted values. Noted for honesty: an authenticated session already holds the full command surface, so this is defence in depth, not a boundary. |
| T-08-11-03 | Information Disclosure | `ConfigDto` `#[derive(Debug)]` | low | accept | Neither new field is secret — one is an enum label, one a small integer — so the existing `Debug` derive and its justifying comment remain accurate. |
| T-08-11-04 | Denial of Service | the two setters' save-then-commit ordering | low | mitigate | A failed disk write must not leave in-memory config disagreeing with disk, or the user's next read would lie. Task 1 preserves `do_update_ui_variant`'s clone-save-then-assign order and adds a "does not mutate state when save fails" test for the mode setter. |
| T-08-11-05 | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — no package is installed in any of the three crates or in npm. Every construct used (`serde` defaults, axum handlers, `#[tauri::command]`) already exists in the codebase. No package-legitimacy checkpoint required. |
</threat_model>
