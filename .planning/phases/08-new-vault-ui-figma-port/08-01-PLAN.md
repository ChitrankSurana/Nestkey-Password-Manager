<task type="checkpoint:decision" gate="blocking-human">
  <decision>How does a user get back to Classic if the New interface fails to mount?</decision>
  <context>
    Task 3 empties `tauri.conf.json`'s static `windows` array and builds the window inside
    `.setup()` from `config.ui_variant`. That choice is already made — D-03 records the developer
    selecting it, and this checkpoint is not re-asking it.

    What D-03 does not settle is the recovery path it creates. Once `ui_variant` is `"new"`, the
    only in-app control that can set it back to `"classic"` lives inside the New UI's own Settings
    pane. If the new frontend fails to mount — a missing bundle, a JS error at module scope — the
    window shows nothing and there is no route back from inside the app. Reverting the code is
    also not a clean undo: a Classic build with a static `windows` array ignores `ui_variant`
    entirely, so a user who chose `"new"` silently loses the choice rather than having it honoured.
  </context>
  <options>
    <option id="doc-only">
      <name>Manual config edit is the documented escape</name>
      <pros>Zero extra code and zero new surface. `~/.pwmgr/config.json` is plain JSON and every other preference in this app already behaves exactly this way. The snap-to-default load path added in Task 3 already guarantees a malformed value cannot brick the app.</pros>
      <cons>A user staring at a blank window has to locate and hand-edit a JSON file in their home directory to recover.</cons>
    </option>
    <option id="asset-guard">
      <name>Window builder falls back to index.html when the requested entry asset is absent</name>
      <pros>A missing or renamed bundle can never produce a dead window; the fallback is a few lines inside the same match arm and adds no new permission or plugin.</pros>
      <cons>Only covers the missing-asset case. If the file exists but its JavaScript throws, the window still mounts empty and the manual edit is still the escape.</cons>
    </option>
    <option id="keybind-escape">
      <name>Global shortcut that rewrites ui_variant to classic and relaunches</name>
      <pros>Full in-app recovery with no file editing.</pros>
      <cons>Needs a new capability grant plus the process plugin that D-07 explicitly deferred, and adds a globally-registered key handler — the largest new attack surface for the least likely scenario.</cons>
    </option>
  </options>
  <resume-signal>Select: doc-only, asset-guard, or keybind-escape</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `~/.pwmgr/config.json` → Rust process | A plain-text, user-writable JSON file on disk is read at boot and now decides which frontend asset the desktop window loads. Its contents are attacker-influenceable by anything that can write to the user's home directory. |
| Tauri window label → capability grants | `src-tauri/capabilities/default.json` grants clipboard-manager and dialog permissions to the window labelled `main`. The label is now chosen in code rather than declared in config. |
| Browser/webview → Rust commands | Unchanged from today: every frontend call crosses the IPC or same-origin HTTP seam in `src/lib/api.ts`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Tampering | `src-tauri/src/lib.rs` window-entry resolution from `config.ui_variant` | high | mitigate | The config value is never interpolated into a path. `Config::load()` snaps any value outside `VALID_UI_VARIANTS` to `classic` before the value is ever read, and the builder maps it through a `match` with a catch-all arm returning the fixed literal `index.html`. A hand-edited or corrupted value can therefore only select one of two compiled-in filenames, never an arbitrary local file. Verified by the config snap-to-default test and by the acceptance criterion forbidding path interpolation. |
| T-08-02 | Elevation of Privilege | Tauri window label vs `src-tauri/capabilities/default.json` | high | mitigate | The label argument is the literal `"main"`. Any other label silently drops the clipboard-manager and dialog grants — a failure mode with no error message, degrading secret copy (which carries the 30s auto-clear guarantee) into a silent no-op. Gated by `grep -c '"main"' src-tauri/src/lib.rs` plus the human-check that copies a secret and opens a file dialog. |
| T-08-03 | Denial of Service | Runtime window construction replacing the static `windows` array | medium | mitigate | If `.build()` fails the app has no window and no route back. The `?` propagates the error out of `.setup()` so the failure is loud rather than a silent blank window, and the recovery path is settled by the decision checkpoint in this plan. |
| T-08-04 | Information Disclosure | `newui.html` served by the localhost web portal at `/newui.html` | low | accept | The new entry is served by the portal's existing `ServeDir` fallback and is subject to the same session and CSRF layers as `index.html`; it exposes no route the portal does not already expose. No new surface. |
| T-08-SC | Tampering | npm / cargo package installs | low | accept | This plan installs no new packages in either ecosystem — every dependency it uses (react, react-dom, vite, tauri, serde) is already in `package.json` / `Cargo.toml`. No package-legitimacy checkpoint is required because there is no install task to gate. |
</threat_model>

## Architectural Generalization Note

Before this phase the app had one frontend entry per binary, fixed at build time
(`index.html` for the main binary, `viewer.html` for the viewer). This plan generalizes that
to **one entry per binary, user-selectable at runtime, persisted in config, applied at next
launch**. This is a promotion of the existing concept, not a parallel mechanism bolted
alongside it: D-03 removes the static `windows` array rather than leaving it in place, so
runtime construction becomes the single source of the window for the main binary. The viewer
binary keeps its fixed entry and is explicitly excluded (D-06).

## Planner Assumptions

- **P-01 — `site.notes` and `credential.remarks` render in the new detail panel.** The UI-SPEC's
  `## UI Considerations` leaves this unresolved. Decision: **render both**. Rationale — both
  fields exist in the DTOs, `SiteEditor` already lets a user write `notes`, and nothing in the
  app has ever displayed them, so today the data is write-only. The three-pane detail column has
  the vertical space the old modal did not. Implemented in plan 08-04 with `whitespace-pre-wrap`;
  leaving it ambiguous would leave `DetailPanel`'s layout undefined.
