<objective>
Close G-08-3, the phase's only blocker: `pwmgr_core::vault::CustomField` is missing
`#[serde(rename_all = "camelCase")]`, so every `add_credential` / `update_credential` call
carrying a non-empty custom field fails deserialization at the transport layer before any
business logic runs. The frontend sends `fieldType`; the backend expects `field_type`.

Purpose: unblocks custom fields entirely (add/edit) on both desktop and web, and unblocks the
hidden-custom-field reprompt sub-check that UAT Test 4 could not exercise.

Output: a one-attribute fix plus JSON-level regression tests, including a backward-compatibility
test for vaults that already hold custom fields.
</objective>

  <behavior>
    Add these tests to `core/src/vault.rs`'s existing `#[cfg(test)] mod tests` block
    (it starts at line 666 and already has `use super::*;`). Write them FIRST and confirm they
    fail before touching the struct.

    - `custom_field_deserializes_camel_case_field_type`:
      `serde_json::from_str::<CustomField>(r#"{"label":"PIN","value":"1234","fieldType":"hidden"}"#)`
      returns Ok, and `.field_type == CustomFieldType::Hidden`.
    - `custom_field_serializes_field_type_as_camel_case`:
      `serde_json::to_string(&CustomField { label: "PIN".into(), value: "1234".into(), field_type: CustomFieldType::Hidden })`
      produces a string containing `"fieldType"`.
    - `custom_field_still_deserializes_legacy_snake_case_key`:
      `serde_json::from_slice::<Vec<CustomField>>(br#"[{"label":"PIN","value":"1234","field_type":"hidden"}]"#)`
      returns Ok with one element whose `field_type == CustomFieldType::Hidden`. This is the
      exact shape `open_custom_fields` sees after decrypting a blob written by any build
      predating this fix — a vault holding custom fields must keep opening.
  </behavior>
  <action>
    Add `#[serde(rename_all = "camelCase")]` to the `CustomField` struct declaration in
    `core/src/vault.rs` (directly above `pub struct CustomField`, matching how `CustomFieldType`
    immediately above it is already annotated). Keep the existing `#[derive(Clone, PartialEq,
    Serialize, Deserialize)]` line and the existing head comment about `Hidden` values being as
    sensitive as the main secret.

    Then add `#[serde(alias = "field_type")]` on the `field_type` member itself. This is
    load-bearing and is NOT optional: `seal_custom_fields` serializes the field list with
    `serde_json::to_vec` and encrypts the result, and `open_custom_fields` deserializes it back
    with `serde_json::from_slice`, mapping any failure to `VaultError::UnlockFailed`. Every
    credential already saved with a custom field therefore holds a blob keyed on the old
    snake_case name. Without the alias, renaming the wire key would make those existing
    credentials fail to decrypt — turning a transport bug into silent data loss. The alias makes
    reads accept both spellings while writes emit only the new one.

    Do not change `CustomFieldType`, `seal_custom_fields`, `open_custom_fields`, `add_credential`,
    `update_credential`, or `list_credentials_for_site` — the defect is purely the missing
    rename attribute, and the transports (`src-tauri/src/commands.rs`,
    `web-src-tauri/src/handlers.rs`) already deserialize this same struct with no local copy.
  </action>
  <verify>
    <automated>cargo test -p pwmgr-core custom_field</automated>
    <automated>grep -c 'rename_all = "camelCase"' core/src/vault.rs</automated>
    <automated>grep -c 'alias = "field_type"' core/src/vault.rs</automated>
  </verify>
  <done>
    All three new tests pass. A JSON payload using `fieldType` deserializes into `CustomField`,
    serialization emits `fieldType`, and a legacy payload using `field_type` still deserializes.
  </done>
