<task type="checkpoint:decision">
  <name>Task 1: Decide cascade-restore semantics before changing core delete behavior</name>
  <decision>
    Making `soft_delete_site` cascade is straightforward. What it does to Trash is not, and the
    UAT diagnosis for G-08-6 explicitly lists this as an open product decision.

    Today `list_trash` joins credentials to sites WITHOUT filtering on the site's own
    `deleted_at`, so once a site is cascade-deleted its credentials WILL appear in Trash under the
    deleted site's name. But `restore_credential` only clears the credential's `deleted_at`, and
    `list_credentials_for_site` filters on `s.deleted_at IS NULL` — so a restored credential whose
    site is still deleted becomes live-but-unreachable. There is no restore-site UI anywhere in
    the app. That orphan state is exactly why the refuse-outright guard was written in the first
    place, so it has to be answered before the guard comes out.

    **Option A (recommended): restoring a credential revives its site.**
    Cascaded credentials stay visible in Trash. `restore_credential` additionally clears
    `deleted_at` on that credential's site if the site is deleted. Nothing is ever orphaned, the
    existing Trash screen needs no change, and the user gets a real undo path for an accidental
    cascade delete. Cost: one extra UPDATE and one test.

    **Option B: cascaded credentials stay in Trash but restoring one does NOT revive the site.**
    Least code, but reintroduces the orphan state the guard existed to prevent. Not recommended.

    **Option C: hide cascaded credentials from Trash entirely.**
    Add `AND s.deleted_at IS NULL` to `list_trash`. Clean list, but a cascade delete becomes
    permanently unrecoverable with no warning. Not recommended.

    Recommendation: **Option A.**
  </decision>
  <options>
    - A: restoring a cascade-deleted credential also revives its site (recommended)
    - B: cascaded credentials are restorable but their site stays deleted (orphan state returns)
    - C: cascaded credentials are hidden from Trash and effectively unrecoverable
  </options>
  <impact>
    Determines whether Task 2 also modifies `core::vault::restore_credential` (Option A), changes
    nothing else (Option B), or modifies `core::vault::list_trash` (Option C). Also determines the
    exact wording of the cascade confirmation copy written in Tasks 3 and 4 — Option A can
    truthfully say the credentials move to Trash and can be restored; Option C cannot.
  </impact>
  <default_if_unanswered>A</default_if_unanswered>
  <resume-signal>Reply "A", "B" or "C" (or "approved" to take the recommended Option A)</resume-signal>
</task>
