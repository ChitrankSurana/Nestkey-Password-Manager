<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| New UI → existing editor overlays | `SiteEditor` and `CredentialEditor` carry their own validation and their own destructive-confirmation copy; the new UI mounts them rather than reimplementing either. |
| New UI → existing secondary screens | `Settings`, `Data` and `Trash` expose privileged operations (PIN, biometric, SSH keys, backup/restore, purge). They are reused unmodified, so their existing platform gating comes along. |
| Destructive action → user intent | Site deletion and trash purge are irreversible; credential deletion is a reversible soft delete. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-19 | Tampering | Destructive confirmations in the new UI | high | mitigate | The confirmation copy is not re-authored. Site deletion keeps `SiteEditor`'s own `window.confirm` with its exact existing string, and trash purge keeps its own inside the reused `Trash` screen. Duplicating or rewording either in the new UI would let the two paths drift, with the weaker one becoming the attack path. Gated by a zero-match grep for a confirm call anywhere under the new UI and by the diff check that no reused screen was edited. |
| T-08-20 | Elevation of Privilege | `SettingsPane` in the web portal | high | mitigate | `Settings` is reused byte-for-byte, so its existing `isTauri` gating on biometric and SSH-agent controls still applies. Re-implementing or forking the Settings markup for the new shell would be the way that gating gets lost; the wrapper is a one-line passthrough and the diff check enforces that the original is untouched. |
| T-08-21 | Repudiation | Credential deletion with no confirmation | low | accept | Deliberate parity with today's behaviour: the delete is a soft delete, fully restorable from Trash, and adding a prompt here while Trash exists would be friction without a safety gain. The irreversible step — purge — keeps its own prompt inside the reused screen. |
| T-08-22 | Spoofing | Per-item health presentation | medium | mitigate | The strength block links out to the real vault-wide Health Dashboard instead of rendering a per-item breach or reuse verdict the backend never computed. Gated by the acceptance criterion that the block still shows neither status. |
| T-08-23 | Information Disclosure | Editor overlays above a three-pane shell | low | accept | The existing `fixed inset-0 z-50` overlay covers the panes behind it; no pane is `fixed`, so nothing can render above the overlay and shoulder-surf the form. No change from today's stacking. |
| T-08-SC | Tampering | npm package installs | low | accept | This plan installs no new packages. No package-legitimacy checkpoint is required because there is no install task to gate. |
</threat_model>

scope, narrowed by CONTEXT.md D-10 with explicit developer confirmation. Item types,

or command exists, and D-10 forbids shipping them as disabled stubs. Per-item health is
**partially delivered** (strength meter only, plan 08-04). Full breakdown in
`08-01-PLAN.md` → `## Requirement Scope Note`.
