<objective>
Close the last handler of SECURITY_CONCERNS.md H1 (SEC-01): web-mode `restore_backup` stops accepting
a client-supplied path. The browser uploads the `.bak` bundle; the server restores from the cached
bytes (D-05).

Purpose: `restore_backup` is H1's remaining read-and-overwrite primitive — it reads an
attacker-named path and can replace a vault file. Removing the path parameter removes it structurally
(D-01/D-05). This plan also carries the phase-level SEC-01 closure gate: after it lands, none of H1's
four named handlers accepts a destination from the client.
Output: a path-free core restore function, a raw-bytes `/api/upload_backup` route reusing the
`UploadCache` from plan 09-02, an `isTauri`-branched `Backup.tsx::handleRestore`, and integration
tests covering the happy path, the confirmation round trip, the no-upload case and the SEC-01 closure
assertion across all four handlers.
</objective>

`09-CONTEXT.md` D-01/D-05 override that with the full upload redesign. This plan implements D-01/D-05.

## Deferred (explicitly out of scope, no task)

Web-mode `create_backup` writes the backup into the server's own backups directory and returns that
server-side path to a browser that cannot fetch it. That is a real pre-existing usability gap, but it
is **not** one of H1's four named handlers, it never accepted an attacker-controlled path, and Phase
08 Plan 10 deliberately kept it server-side-only for web mode. It stays out of Phase 9. Do not add a
task for it, and do not change `create_backup`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `pwmgr-web` HTTP API | Untrusted raw backup bytes from any process reaching `127.0.0.1:7373`. |
| `pwmgr-core` restore layer → vault files + `registry.db` | The most destructive write path in the product: it replaces a vault file and upserts a registry row. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-12 | Tampering | `restore_backup` reading and overwriting an attacker-named path (H1) | critical | mitigate | Task 1 removes the source field from `RestoreBackupRequest` and restores from the session cache; Task 2's `no_web_handler_accepts_a_client_supplied_destination` is the standing regression gate. |
| T-09-13 | Tampering | A malformed or hostile upload corrupting an existing vault | high | mitigate | `decode_bundle` validates before anything is written, and the existing temp-write / registry-upsert / atomic-rename ordering is preserved verbatim; `restore_backup_rejects_a_non_backup_upload` asserts no vault file appears. |
| T-09-14 | Tampering | An accidental overwrite of a live vault without user consent | high | mitigate | The `already_exists` check still returns `confirm_required` (409) before any write; the frontend still routes it through `confirmDialog`; proven by `restore_backup_confirm_roundtrip_reuses_the_single_upload`. |
| T-09-15 | Information Disclosure | Uploaded bundle bytes persisted to a temp file or echoed in an error | high | mitigate | Bytes stay in the `Zeroizing` session cache; restore errors reuse the existing fixed sanitized messages and never include a path. Cache cleared on restore success. |

| T-09-SC | Tampering | npm/cargo dependency supply chain | low | accept | Zero new packages in this plan. No `[ASSUMED]`/`[SUS]` package, so no package-legitimacy checkpoint applies. |
