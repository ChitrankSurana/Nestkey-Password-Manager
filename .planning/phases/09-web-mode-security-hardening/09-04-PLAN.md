<objective>
Close SECURITY_CONCERNS.md M1 and M2 (SEC-02): the localhost web server throttles repeated failed
credential attempts with a doubling lockout window, and bounds concurrent Argon2 derivations so a
request burst cannot exhaust server memory.

Purpose: today `/api/login` and `/api/register_user` have no attempt limit at all, and every attempt
allocates a 64 MiB Argon2 derivation with no concurrency cap — so a local process can both
brute-force the master password and flood the machine's RAM, for free, with no authentication.
Output: a new in-process `ThrottleStore` implementing D-08's exact window shape, a shared `KdfGuard`
semaphore, two new sanitized error codes mapped to HTTP 429, wiring on every Argon2-driving web
route, and a code-aware client retry.
</objective>

## Planner Decisions (Claude's Discretion, recorded here)

`09-CONTEXT.md` explicitly delegates these four values. They are locked here; do not re-open them
during execution.

| Constant | Value | Rationale |
|---|---|---|
| `FAIL_THRESHOLD` | `5` | Verbatim from D-08. |
| `BASE_WINDOW` (`W`) | `30s` | M1 is about online brute force against a single-user loopback server, not a distributed attacker. 30s meaningfully slows automated guessing without punishing a user who mistypes five times in a row. |
| `MAX_WINDOW` (doubling cap) | `1h` | Bounds the worst case for a forgetful legitimate user at "never locked out more than an hour" while still imposing serious friction on a sustained attacker. The sequence is 30s, 1m, 2m, 4m, 8m, 16m, 32m, 60m, 60m, ... |
| `KDF_PERMITS` | `3` | D-12's range is 2-4; 3 is SECURITY_CONCERNS.md M2's own suggested value. Worst-case memory is 3 x 64 MiB = 192 MiB regardless of burst size (`core/src/crypto.rs` uses `m=65536` KiB). |

**Store shape divergence from 09-PATTERNS.md's sketch (deliberate).** PATTERNS sketches
`check` / `record_failure` / `record_success`. A separate check-then-later-record pair has a
time-of-check/time-of-use gap: N parallel attempts all pass `check` before any of them records a
failure, so a concurrent burst can exceed the threshold. This plan instead uses a single
`begin_attempt` that makes the lock decision **and** increments the counter inside one write-lock
critical section, with `record_success` clearing the key afterwards. Same D-08/D-09/D-10 semantics,
no TOCTOU gap.

**Scope extension beyond the literal text of D-07 and D-13 — flagged for the developer.**
`09-CONTEXT.md` D-07 names `/api/login` and `/api/register_user`; D-13 names `login`,
`register_user` and password-mode `export_csv`. Reading the code during planning surfaced a **fourth
pre-auth Argon2 route neither the audit nor the decisions name**: `/api/unlock_with_pin` reaches
`core/src/auth.rs::unlock_with_pin`, which calls `crypto::derive_key` (the same 64 MiB derivation) on
a user-supplied PIN — a shorter, more brute-forceable secret than the master password. Leaving it
uncovered would make SEC-02's own locked wording ("concurrent Argon2 derivations are bounded so a
request burst cannot exhaust server memory") false, and would leave the weakest credential on the
server unthrottled while the strongest is throttled. This plan therefore extends **the same** throttle
store and **the same** shared semaphore to `/api/unlock_with_pin`. No new mechanism, no new
dependency, no change to D-08's shape. Record this in the plan SUMMARY.

**Consequence of D-09 on a loopback-only server — accepted, documented, not silently altered.**
`pwmgr-web` binds `127.0.0.1` exclusively, so every request's peer address is the loopback address.
The IP key therefore behaves as a single machine-wide counter: five failed attempts across any
usernames lock all credential routes for the current window. D-09 is a locked decision and is
implemented exactly as written. The user-facing message is worded to make this legible ("Too many
failed attempts from this machine."), and the effect is bounded by `MAX_WINDOW` and cleared by the
next success (D-10). See T-09-22 in the threat register.

Create `web-src-tauri/src/throttle_store.rs` mirroring `session_store.rs`'s shape, importing
`std::collections::HashMap`, `std::sync::{Arc, RwLock}`, `std::time::{Duration, Instant}` and
`pwmgr_core::session::Clock`. Declare `pub const FAIL_THRESHOLD: u32 = 5;`,
`pub const BASE_WINDOW: Duration = Duration::from_secs(30);`,
`pub const MAX_WINDOW: Duration = Duration::from_secs(60 * 60);` and
`pub const THROTTLE_PRUNE_AFTER: Duration = Duration::from_secs(24 * 60 * 60);`.

Define a private `ThrottleEntry` carrying `fail_count: u32`, `current_window: Duration`,
`locked_until: Option<Instant>` and `last_seen: Instant`, and
`#[derive(Clone, Default)] pub struct ThrottleStore` wrapping `Arc<RwLock<HashMap<String, ThrottleEntry>>>`.

`pub fn begin_attempt(&self, key: &str, clock: &dyn Clock) -> Result<(), Duration>` does all of the
following in ONE write-lock critical section, in this order:
1. Read `clock.now()`, get-or-insert the entry with `fail_count` 0, `current_window` equal to
   `BASE_WINDOW`, no lock, and `last_seen` now; then refresh `last_seen`.
2. If the entry is locked and now is before the lock expiry, return the remaining duration as the
   error — still locked, and nothing is incremented.
3. If the entry is locked and the expiry has passed, clear the lock and reset `fail_count` to 0 — a
   new cycle begins.
4. Increment `fail_count`. When it reaches `FAIL_THRESHOLD`, set the lock expiry to now plus
   `current_window`, reset `fail_count` to 0, then advance the window for the NEXT cycle with
   `current_window.saturating_mul(2).min(MAX_WINDOW)`. Use `saturating_mul`, never plain
   multiplication — a `Duration` overflow panic while holding the write lock would poison the map and
   brick every credential route (09-RESEARCH.md Pitfall 6).
5. Return success.

Counting at attempt start rather than on failure is what closes the time-of-check/time-of-use gap:
five parallel attempts each increment atomically, so the sixth is refused even while the first five
are still in flight. Document that guarantee in a doc comment on `begin_attempt`.

`pub fn record_success(&self, key: &str)` removes the entry outright — that resets the failure count,
the window multiplier and any lock in one step (D-10). `pub fn sweep(&self, clock: &dyn Clock)` takes
the write lock once and retains entries that are either currently locked or were seen within
`THROTTLE_PRUNE_AFTER`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any local process → `pwmgr-web` pre-auth routes | `/api/login`, `/api/register_user`, `/api/unlock_with_pin` are reachable with no credential at all by anything that can open a loopback socket. |
| HTTP handler → `pwmgr-core` KDF | Each crossing allocates 64 MiB of Argon2 memory; the crossing rate is the resource-exhaustion surface. |
| Throttle store → every credential route | A poisoned or wedged throttle map would deny service to the legitimate user, so its failure mode matters as much as its enforcement. |
