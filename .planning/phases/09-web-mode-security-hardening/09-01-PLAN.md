<objective>
Close the export half of SECURITY_CONCERNS.md H1 (SEC-01): the web-mode `export_csv` endpoint stops
accepting a client-supplied destination and stops writing a server-side file. The export bytes are
returned in the HTTP response body and the browser saves them.

Purpose: `export_csv` is the most dangerous half of H1 — in plaintext mode it writes the *decrypted
vault* to any path an authenticated web client names. Removing the path parameter removes the
vulnerability structurally: there is no path validation to get subtly wrong because there is no path
(D-01).
Output: two new path-free core functions, a rewritten web `export_csv` handler, a `httpDownload`
transport helper, an `isTauri`-branched `CsvExport.tsx`, and HTTP integration tests proving both the
positive (bytes come back) and negative (no file is created) behavior.
</objective>

## Requirement Scope Note

`.planning/ROADMAP.md` Phase 9 success criterion #1 and `REQUIREMENTS.md` SEC-01 both describe
**path confinement** ("reject any client-supplied path that isn't a filename inside the app's own
backups/exports directory"). `09-CONTEXT.md` **D-01 deliberately overrides that** with the stronger
fix: a full upload/download redesign in which no server-side path is ever named by a web client, with
no filename-only allowance either. This plan implements D-01. A review that diffs this plan against
the ROADMAP/REQUIREMENTS wording alone must not revert it to path confinement.

## Planner Decisions (Claude's Discretion, recorded here)

- **Raw request/response bodies, not multipart** (resolves 09-RESEARCH.md Open Question 3). All four
  redesigned handlers in this phase use raw bytes over the HTTP body: zero new Cargo dependencies,
  and every flow in this phase sends the file alone (format/confirmed are always separate follow-up
  JSON calls per D-03). This choice is applied consistently across plans 09-01, 09-02 and 09-03.
- **Export filenames**: `vault-export.csv` for plaintext mode, `vault-export.pwenc` for both
  encrypted modes — matching the `defaultPath` values `CsvExport.tsx` already uses on desktop.

## Deferred (explicitly out of scope, no task)

Web-mode `create_backup` writing a server-side file the browser cannot download is a real,
pre-existing usability gap (`web-src-tauri/src/handlers.rs` line ~577). It is **not** one of H1's four
named handlers, it never accepted an attacker-controlled path, and Phase 08 Plan 10 deliberately
decided to keep it server-side-only for web mode. It stays out of Phase 9. Do not add a task for it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `pwmgr-web` HTTP API | Untrusted JSON request bodies from any process that can reach `127.0.0.1:7373`, including an XSS in the SPA itself. |
| `pwmgr-web` handler → `pwmgr-core` command layer | The handler decides what the core layer is asked to do with the unlocked vault key. |
| `pwmgr-core` → local filesystem | Where H1's arbitrary write landed. This plan severs the web branch of this boundary for export. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Tampering | `export_csv` web handler → `std::fs::write` (H1) | critical | mitigate | Task 1 removes the destination field from `ExportCsvRequest` and rewrites the handler to return bytes; Task 2's `export_csv_writes_no_server_side_file_for_a_crafted_destination` test is the standing proof. |
| T-09-02 | Information Disclosure | Plaintext export = decrypted vault dropped at an attacker-chosen path | critical | mitigate | Same as T-09-01; additionally the plaintext confirmation gate is re-asserted over the web transport by Task 2's rejection test. |
| T-09-03 | Information Disclosure | Export bytes persisted server-side (temp file / log body) | high | mitigate | `do_export_csv_bytes` performs no filesystem access; the plaintext-export log records only a fixed label, never the export contents.
